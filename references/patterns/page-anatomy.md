Page Anatomy is FlowX's page-composition pattern: it says how platform pages are put together rather than specifying pixels. Assemble new pages from its named parts instead of inventing a layout. The building blocks are four page levels signalled by the navigation frame, a shared title-card + main-card spine, three resource-list render modes, the regular resource page layout, and four main-card variants. Nearly every page is a title card that names the resource followed by the content below it (usually a single main card); the only pages without this spine, such as canvas editors, are deliberate exceptions. Everything sits on the grey app background (neutrals-50, #f7f8f9). The wireframes on the page are illustrative skeletons, not authoritative measurements — for the exact surfaces this pattern composes, read cards.json (Primary and Secondary cards), values-table.json (tables), tabs.json (tab bars), button.json (footer and inline actions), and empty-states.json (empty lists and result panes).

The four page levels. Every screen sits at one of four levels, and the navigation frame tells you which one; the higher the level the more navigation is present, and drilling into a resource replaces the nav with a back breadcrumb. Workspace / Org level has no top command bar: a left sidebar carries the brand, the workspace or organization switcher, the labelled nav, and the user profile pinned at the bottom, and a system alert banner may sit above the content (real examples: Projects, Platform Status, Audit Logs, Usage Stats, Branding). Project level adds the top command bar together with the full labelled left nav, a page title card, and the resource list (real examples: Processes, Data Sources, Views, UI Flows). Inside a resource, canvas shows a subheader with a back breadcrumb, the nav collapsed to an icon rail, and a full-width canvas with side panels (real examples: Process Designer, UI Designer, Data Model). Inside a resource, regular page shows a subheader with a back breadcrumb (which can run two to four levels deep and is the way back out) and the regular resource page body of a title card plus main card (real examples: REST data source detail, connection settings).

Resource list render modes. A resource list can be laid out three ways whatever it contains, and the layout is a treatment rather than a new page — the title card and the spine stay the same. Tables puts one or more tables inside the main card, each under its own sub-header, and is the default layout for entity lists (uses the Values Table / Tables component). Nested cards puts a grid of Secondary cards inside the main card, one per entity, each with its own inline actions. Primary cards drops the main card entirely and makes each entity its own Primary card, stacked directly under the title card.

Regular resource page. It has one spine: a title card that names the resource, followed by the content below it. The main option is one title card and one main card holding all the content, the default for records and settings. The variant replaces the main card with a grid of small cards, one per entity or capability, each with its own inline actions, used when the content is a set of independent peers (real examples: Model Providers, capability defaults).

Main card variants. The main card comes in four variants chosen by how much the resource carries; when a record has more than a couple of fields, its one or two defining fields stay in the top card (which becomes a config card) and everything else moves into tabs. Without tabs is a single group of fields with footer actions (Reset / Save bottom-right), for simple one-facet resources such as a connection form. With tabs makes the top card a config card that keeps the defining field while a tab bar in the main card splits the rest into facets, each tab holding its own content such as a table with its own Add action. With tabs and columns puts peer sections in two columns inside a tab when they have no natural order; a section header can carry an enable toggle that gates the whole section, and a section toggled off collapses to its header. With a split pane splits the tab content in two for operation editors — inputs on the left, live output on the right, such as a code preview, a results console, or a query builder (real examples: SOAP operations, database find operations).

Ground rules (the templates above are these rules made concrete; when a new page does not fit an existing template these still apply). Title card, then main card: the spine of nearly every page, with the few exceptions like canvas editors being deliberate. Identity first, details in tabs: the one or two defining fields sit in the top config card, everything else goes into a tab. Commit in the footer, act in the section: Reset and Save sit bottom-right of the main card, local actions like Add or Test sit next to what they change, and nothing floats in between. Stack when order matters, columns when it doesn't: sections that depend on each other read top to bottom, peers with no natural sequence can share a row. Show state before detail: enable toggles gate sections and status pills mark rows, so state is visible before anything is opened. No page renders blank: every list ships an empty state and every result pane says what to do first (see the Empty States pattern). Related patterns and components are Cards, Values Table / Tables, Tabs, and Empty States. Dark-theme values are not documented; the pattern page keeps its wireframes light.
